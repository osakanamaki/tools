## marimo固有の注意事項

### 関心の分離の徹底

marimoはセルの依存関係によって処理が自動実行される。
安定した動作のためには、セルは単純でなければならない。

* レイヤーの関心分け
  * `src/core` : 純粋なビジネスロジック
  * `src/components` : 共通UIコンポーネント
  * `src/apps` : アプリケーション統合 / GUI
* セルの関心分け
  * 「変数のまとまり（データコンテキスト）」x「以下の役割」に応じてセル(`@app.cell`)を分割
    * 変数宣言
    * 画面表示
    * 処理1実行
    * 処理2実行
    * ...

### 静的解析

`task lint` は以下の要素においてエラー終了する。

* セル名がない（`def _`）。
* DocStringがない。
* UI要素がどこからも参照されていない。
* `mo.ui.run_button` の `.value` がどこでも参照されていない。
* `docs/flows/` の図がコードより古い。
* その他、一般的なPython・マークダウン記述ルールの違反。

また、効率的なセル記述のため `src/apps/*` に対して `tool.ruff.lint.per-file-ignores` を設定している
( `pyproject.toml` 参照)。

### テスト観点

|レイヤー|カバレッジ計測の価値|テスト方針|
|---|---|---|
|`src/core`|高|単体テストによる品質担保|
|`src/components`|中|コンポーネントの責務検証|
|`src/apps`|低|カバレッジテストは品質保証にならない。後述|

* `src/apps` はカバレッジを満たしても、DAGの実行順序やリアクティブな挙動の保証にはならない。
* `src/apps` は以下で保証する。
  * 「実際の挙動」
    * `task app` で起動し、各入力要素の空入力・異常値・連打を確認する。
  * 「DAGの健全性」
    * `task flow` でMermaidフロー図を出力できる。これを用いて全体像を俯瞰する。PRでは `docs/flows/*.md` の差分として確認できる。
    * 複雑すぎる交差、巨大すぎる集中ノードが存在しないか（依存関係の疎結合化）を視覚的にレビューする。
  * 「フレームワークの正しい利用」
    * キャッシュ戦略は適切か。
    * 日付、数値、ラジオボタン...入力要素は適切か。この検討はUX向上にも、バリデーションを減らすためにも必要である。
    * マークダウンやhtml、styleを冗長に使用していないか。
    * `mo.state` は宣言的なデータフローを壊すため使うべきでない。
    * 実行制御に意図はあるか。 `mo.form` はスマートである。 `mo.run_button & mo.stop` は事前バリデーションができる。
